## CORE ARCHITECTURE

**Primary Abstraction:** Field-selective API proxy

FieldFlow operates as a middleware layer that wraps OpenAPI-described REST endpoints and allows callers to request ONLY the fields they need. Rather than receiving full API responses, clients specify `fields` parameter and get back only the selected data.

**Mechanism:**
- Auto-discovers endpoints from OpenAPI 3.0 spec
- Generates Pydantic request/response models dynamically
- Wraps endpoints with FastAPI proxy routes
- Uses httpx to forward requests upstream
- Filters response JSON to requested fields
- Handles nested schemas and $ref resolution

**Operational Modes:**
1. **HTTP mode** (`fieldflow serve-http`) — Exposes REST endpoints on localhost; tools access via HTTP requests
2. **MCP mode** (`fieldflow-mcp`) — Surfaces same tools via Model Context Protocol; Claude Desktop direct integration

**State Management:** Stateless proxy architecture
- No persistent state maintained
- Each request is independent
- Configuration via environment variables (auth credentials, upstream URLs)
- Credentials sanitized from logs

**Communication Pattern:** Synchronous HTTP request/response
- Caller → FieldFlow → Upstream API
- Blocking calls; simple request/reply semantics
- Suitable for tool-like consumption (Claude function calls)

**Error Handling:**
- httpx error propagation (network failures, timeouts)
- Pydantic validation errors on response parsing
- Field reference errors (requesting non-existent fields)
- No explicit retry logic documented; relies on caller
- Credentials validation at startup (environment check)

**Extensibility:**
- OpenAPI spec drives all behavior (auto-discovery)
- Auth schemes defined in OpenAPI spec auto-wired
- CLI mode available for JSON-emitting commands (GitHub CLI, gcloud, kubectl, aws)
- Companion `fieldflow-cli` wraps shell commands with field filtering

**Authentication Support:**
- Bearer tokens / JWT
- API keys (custom header support)
- Basic authentication
- OpenAPI-defined security schemes
- All credentials environment-configured; automatic sanitization

## THUNDERBIRD APPLICABILITY

**Strongest Match:** Token efficiency across 120+ MCP tools

FieldFlow's core innovation—field-selective API filtering—directly addresses Thunderbird's highest operational pain point: token budget constraints. Every API response that includes unnecessary fields consumes tokens that could go toward higher-value work.

**Pain Points Addressed:**

1. **Token Waste on Verbose API Responses** (CRITICAL)
   - Thunderbird's 120+ MCP tools return full JSON responses
   - Typical example: hotel search returns 50+ fields; Dani only needs name, price, rating, link
   - Documented case (GitHub): 88% payload reduction by filtering
   - **Thunderbird opportunity:** 2,000+ API calls/week × average 40% field utilization = massive waste
   - **Potential savings:** 40-60% reduction in API-related token spend

2. **Cost-Aware Routing (SECONDARY)**
   - FieldFlow filtering could reduce downstream token costs
   - Smaller payloads = smaller context windows = cheaper completions
   - Relevant to Thunderbird's 8-tier cost optimization strategy (Apr 2026)

3. **Response Structure Consistency (TERTIARY)**
   - MCP tool responses vary in field richness
   - FieldFlow normalizes to caller-requested schema
   - Reduces Dani/Hale need to parse/summarize verbose responses

**Integration Points:**

1. **Hotel/Flight/Transfer/Tour Price Scrapers**
   - `/hotel-price`, `/flight-price`, `/tour-price`, `/transfer-price` all return full schema
   - FieldFlow could filter to: `[name, price, rating, link, images]`
   - Immediate impact: Lifecycle ARC1→ARC2→ARC3 cost reduction

2. **MCP Tool Gateway (thunderbird_hotel_search.py, etc.)**
   - Current: All 120+ tools return full responses
   - With FieldFlow: Wrap via HTTP mode, specify needed fields per tool
   - No persona code changes required; transparent proxy

3. **Dani Client Response Construction**
   - Current: Dani receives verbose search results, manually summarizes
   - With FieldFlow: Dani receives pre-filtered results → faster aggregation → fewer tokens

4. **A1 Profile Generation (post-intake)**
   - Image-tap onboarding generates Travel DNA
   - FieldFlow could filter vendor APIs to structure matching A1 requirements
   - Example: Destination API → filter to `[climate, seasonality, visa_requirements, best_time_to_visit]`

**Key Insight:** These are NOT competing systems. They operate at different layers:
- **Kit** = workflow methodology (how Thunderbird structures 90-day client journeys)
- **Patchwork OS** = approval/queue layer (WF-17 draft gate, escalations)
- **FieldFlow** = efficiency layer (token reduction on API calls within workflows)

FieldFlow is **complementary** to both Kit and Patchwork OS. It sits INSIDE workflows (Kit) and could optimize responses before they hit approval queues (Patchwork OS).
