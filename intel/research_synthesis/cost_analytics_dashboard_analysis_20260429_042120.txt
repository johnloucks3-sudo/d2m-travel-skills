## COST/QUALITY METRICS

**Cost Tracking (Both Tools):**
- Input tokens (per-model pricing as of April 2026)
- Output tokens (per-model pricing)
- Prompt cache creation tokens (distinct line item)
- Prompt cache read tokens (distinct line item)
- Session-level cost aggregation
- Daily cost breakdowns
- 7-day moving cost trends
- All-time cumulative cost
- Per-model cost attribution (Opus/Sonnet/Haiku variants)
- Cost estimates based on Anthropic API pricing structure

**Cost Calculation Formula:**
  - claude-usage: Uses official April 2026 Anthropic API pricing rates for input/output/cache
  - NOTE: Max/Pro subscribers are subscription-based; displayed costs reflect API rates for estimation purposes

**Quality Definition (Limited):**
  - **Token efficiency:** Input/output token ratio per session
  - **Cache hit rate:** Prompt cache reads vs writes (indicates reusable context)
  - **Session duration:** Timestamp-based analysis of task-to-completion time
  - **Model selection efficiency:** Tracks which model used for which task (enables cost-per-quality analysis)
  - **Tool usage patterns:** Session replay shows tool invocations (indirect quality proxy)

  **CRITICAL GAP:** Neither dashboard explicitly measures output quality (accuracy, relevance, correctness). Quality metrics are inferred from token patterns and cache behavior, not actual result assessment.

**Trade-off Analysis:**
- cc-lens provides "Cost & Cache Analytics" with stacked visualizations showing cost by model type and cache usage patterns
- claude-usage displays per-session tokens and cost, allowing manual cost-vs-latency trade-off inspection
- Both enable model selection trade-offs (Haiku vs Sonnet vs Opus cost curves visible across all sessions)
- No automated cost-quality optimization logic; requires manual interpretation

**Optimization Logic (Built-in):**
- Neither tool has built-in routing logic or cost-optimization recommendations
- Both provide visibility; decision-making is manual/human-driven
- Potential use: external scripts can query SQLite (claude-usage) or export data to build optimization rules

## DIRECT UTILITY TO THUNDERBIRD

**Primary Use Case:**
Real-time token budget visibility + cost-per-model attribution. Thunderbird currently tracks cost via `thunderbird_usage_monitor.py` (30-min batch), but lacks per-session detail and cache analysis. These dashboards provide:
- Sub-session cost tracking (vs. current 30-min batching)
- Cache hit rates (NEW — currently unmeasured)
- Model-specific cost breakdowns (currently aggregate)
- Per-project cost isolation (critical for multi-TP bookkeeping)

**Secondary Use Cases:**
1. **Model routing decisions:** Visible cost curves across Haiku/Sonnet/Opus enable COS to recommend cheaper models when quality allows
2. **Token burn prediction:** Historical daily cost trends can forecast approaching $100 MAX credit limit (currently alerts at 82% via Poe/Max switcher)
3. **Budget allocation by TP:** If Thunderbird's CLI session naming includes client ID (e.g., session_mcleod_validation_email_v3), dashboard auto-attributes cost to TP
4. **Cache ROI calculation:** Measure prompt cache creation cost vs. savings over 7-day/30-day windows (Sonnet/Opus caching strategy)
5. **Commander cost transparency:** Daily dashboard snapshot to johnloucks3 showing "today's cost by model/project/person" (new intel product)

**Integration Points:**
1. **Session log ingestion:** claude-usage scans `~/.claude/projects/*.jsonl` — Thunderbird already generates these
2. **Database query layer:** SQLite at `~/.claude/usage.db` — COS/EXEC can query for cost-per-TP breakdowns
3. **Web UI replacement:** Could replace `thunderbird_usage_monitor.py` (Windows Electron) with browser-based claude-usage on YOGA
4. **Real-time alerts:** Export database to Telegram C2 via scheduled query (e.g., "Model costs past hour: Opus $3.50 / Sonnet $0.89 / Haiku $0.04")
5. **Mission board integration:** Tag high-cost sessions for Commander review (e.g., Goose + Claude thinking tasks flagged if > $0.50/session)

**Data Flow (Proposed):**
```
Claude Code CLI session (local JSONL)
         ↓
   claude-usage scanner (incremental parse)
         ↓
   ~/.claude/usage.db (SQLite)
         ↓
   [Option A] Web dashboard @ localhost:8080 or https://itinerary.d2mluxury.quest/cost-analytics
   [Option B] cron query → Telegram pager every 30 min
   [Option C] COS custom script → staff brief (e.g., "Cost Snapshot" email to Commander)
```

## IMPLEMENTATION ASSESSMENT

**Architecture:**
- **claude-usage:** Monolithic (single codebase, loosely separated scanner/server/cli). Highly integrable—single Python script, no external deps, SQLite backend is standard.
- **cc-lens:** Distributed (npx-installed package). Also integrable but requires Node.js environment.
- **Thunderbird recommendation:** claude-usage better for server-side (YOGA) deployment; cc-lens better for local developer machines.

**Data Pipeline:**
- **claude-usage:** Real-time file monitoring (incremental scan, modification-time tracking) → SQLite writes. Scan latency: ~100ms (pure Python, local files). Web UI auto-refresh: 30-second intervals.
- **Latency:** Sub-minute (scan → database update → dashboard refresh). **Meets Thunderbird's <5min decision-latency requirement.**
- **Data freshness:** Current session in flight appears after session completes (post-CLI exit). In-progress sessions NOT visible until written to disk.

**Platform Support:**
- **claude-usage:** Linux ✅ (pure Python stdlib), macOS ✅, Windows ✅. No platform-specific code detected.
- **cc-lens:** Linux ✅, macOS ✅, Windows ✅ (Node.js portable).
- **Headless capability:**
  - **claude-usage:** YES. Python HTTP server (default localhost:8080) can run on YOGA in tmux/detached. Can bind to 0.0.0.0 via HOST env var → accessible at https://yoga.internal/ or via Cloudflare tunnel.
  - **cc-lens:** YES. Node.js server also headless-capable; can run on YOGA with port forwarding.

**Integration Complexity:**
- **Easy:** Plug-and-play if used as-is (run `python cli.py dashboard` on YOGA, tunnel to https://itinerary.d2mluxury.quest/costs)
- **Medium:** Embed cost-per-TP logic (rename Claude Code sessions to include client ID → parse in scanner.py)
- **Hard:** Real-time Telegram alerts (requires wrapping SQLite queries in Telegram gateway, ~200 LOC)

**Dependencies:**
- **claude-usage:** Python 3.8+ only. NO external package deps. ~3KB stdlib footprint.
- **cc-lens:** Node.js + npm. Slightly heavier but still minimal (~5MB installed).
- **No external APIs:** Both read local files only. No Anthropic API call required (uses local JSONL logs).
- **No auth required:** Both assume existing Claude Code session logs on disk.

## RISKS & BLOCKERS

**Technical Blockers:**
1. **JSONL log format changes:** If Anthropic changes Claude Code's local transcript format (unlikely, but possible in major version), scanner may break. Mitigation: Monitor phuryn's repo for updates; maintain pin on claude-usage version.
2. **SQLite file contention:** If Claude Code writes logs while scanner runs, lock contention possible (rare, but edge case). Mitigation: Scanner already uses incremental tracking (avoids re-scanning); safe.
3. **Cached pricing rates:** April 2026 API pricing in dashboard code will become stale if Anthropic raises rates. Mitigation: Manual update required (1-line code change every ~6 months or on price change announcement).

**Integration Challenges:**
1. **Session naming convention:** Current Thunderbird sessions don't include TP/project ID. Requires discipline (all CLI launches must follow naming convention). Mitigation: Automate via wrapper script (e.g., `thunderbird-claude -p "..." -TP mcleod` auto-renames session).
2. **Database schema migrations:** If phuryn updates schema, Thunderbird's custom queries may break. Mitigation: Test after phuryn releases; maintain internal query library.
3. **Node.js vs Python:** If cc-lens preferred for UI richness, Thunderbird must maintain Node.js on YOGA. Mitigation: claude-usage sufficient for MVP; cc-lens can be added later.

**Maintenance Burden:**
- **Low.** phuryn maintains upstream; Thunderbird runs as-is. If issues arise, can file issues/PRs on GitHub.
- Monthly check: Verify scanner still runs, database grows, dashboard loads.
- Quarterly: Review cache hit rates, model cost trends, alert calibration.

**Licensing/Dependencies:**
- **License:** phuryn/claude-usage appears open-source (GitHub). Check LICENSE file for commercial use restrictions. Likely permissive (MIT/Apache), but verify before shipping to clients.
- **Dependencies:** Zero external deps (pure Python stdlib). No licensing entanglement.
