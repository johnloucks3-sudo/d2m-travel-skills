## ARCHITECTURE OVERVIEW

### Core Abstraction: Dual-Layer IDE Bridge + Automation OS

**Layer 1 — Claude IDE Bridge** (Foundation):
  - MCP server exposing ~170 tools across 20+ categories
  - Dual WebSocket connections:
    1. Claude Code (or other LLM) ↔ Bridge (MCP JSON-RPC 2.0)
    2. VS Code extension ↔ Bridge (custom request/response protocol)
  - Transport flexibility: WebSocket, stdio, HTTP with Bearer token auth
  - Three CLI binaries from one codebase:
    - `claude-ide-bridge` (bridge-only mode)
    - `patchwork` (full OS with recipes)
    - `patchwork-os` (alias)
  - IDE extensions: VS Code/Cursor/Windsurf extension + JetBrains plugin (49 handlers)

**Layer 2 — Patchwork OS** (Automation):
  - YAML recipe engine defining trigger-action pairs
  - Event triggers: git commits/push/pull, test runs, file saves, cron schedules, manual invocation, webhooks
  - Subprocess agent spawning: Claude (or GPT/Gemini/Grok/Ollama) subprocess handling event-triggered tasks
  - Approval queue: mandatory gate for all writes/external actions
  - Web oversight dashboard at `localhost:3100` + mobile PWA
  - Multi-model routing: Claude, GPT, Gemini, Grok, Ollama via `--claude-driver` flag

### Agent Lifecycle

**Trigger → Recipe Evaluation → Agent Spawn → Execution → Approval → Commit**

1. **Trigger Detection**: File save, git event, cron tick, webhook, manual `/recipe <name>`
2. **Recipe Load**: YAML file matching trigger condition
3. **Agent Spawn**: Subprocess invocation of Claude (or other model) with context injection
4. **Execution**: Agent uses MCP tools to perform writes, external API calls, diagnostics
5. **Approval Queue**: All consequential outputs land in `~/.patchwork/inbox/` for human review
6. **Final Commit**: Approved changes applied atomically via `commitTransaction` tool

### Workflow Model: YAML-Driven, Event-Sourced

```yaml
# Example recipe structure
trigger:
  type: git_commit        # or: test_run, file_save, cron
  condition: "branch == main && message.includes('fix')"
automation:
  model: "claude-sonnet-4.6"
  prompt: |
    Review this commit and suggest refactorings.
  tools:
    - findReferences
    - explainSymbol
    - beginTransaction / stageEdit / commitTransaction
  onApproval: "record decision trace"
  onRejection: "discard and log"
```

Five starter recipes ship production-ready:
  - `ambient-journal`: git commit → append one line to journal
  - `daily-status`: cron 08:00 → morning brief from commit history
  - `watch-failing-tests`: test run → triage note on failure
  - `lint-on-save`: file save → surface new diagnostics
  - `stale-branches`: cron weekly → list aged branches

### State Management: Session Handoff + Decision Traces

**Cross-session persistence** leverages:
  - **Handoff Note**: `~/.claude/ide/handoff-note.json` (10 KB cap per session)
    - Shared across all MCP sessions in a project
    - Holds recent decisions, 12-hour digest, git-aware snapshots
  - **Decision Trace Logs** (JSONL):
    - Records all approvals, enrichments, recipe runs
    - Enables delta comparison via `getDiffFromHandoff`
    - Supports multi-session continuity without explicit context re-injection
  - **Context Bundle** (parallel fetch):
    - Active file + diagnostics + diff + git status
    - Reduces round-trip overhead for agent inspection

**State NOT managed by Patchwork OS**:
  - No dossiers/client profiles (IDE-centric, not business-domain)
  - No mission boards or task queues beyond recipe runs
  - No cross-persona memory (IDE-focused, not multi-agent staffing)
  - No long-running booking lifecycle tracking (IDE, not CRM)

### Communication: Tool Calls + IDE State Push

**Agent → Bridge**: MCP tool invocations (JSON-RPC 2.0)
  - `beginTransaction`, `stageEdit`, `commitTransaction` for atomic multi-file changes
  - `findReferences`, `explainSymbol`, `goToDefinition` for code intelligence
  - `runTerminal`, `runTests`, `getPubStatus` for execution
  - `searchWorkspaceSymbols`, `getCallHierarchy` for navigation

**Extension → Bridge**: IDE state pushed via custom protocol
  - Diagnostics (linter, type checker results)
  - Editor selections, breakpoints, debug state
  - Active file context, git status

**Bridge → Claude**: Structured tool results with pagination support (prevents token bloat)

### Error Handling & Recovery

**Fallback Patterns**: Tools with `extensionFallback: true` degrade gracefully when VS Code extension disconnects:
  - `goToDefinition` → typescript-language-server --stdio
  - `getDiagnostics` → CLI linters (tsc, eslint, pyright, etc.)
  - `searchWorkspaceSymbols` → Universal Ctags or ripgrep

**Explicit Failure Signaling**: Extension-required tools return structured reconnect instructions rather than silently failing—enables clear error reporting to agent.

**Automation Loop Guards**: Conditional triggers via `AutomationCondition` prevent recursive task spawning (e.g., recipe shouldn't trigger itself).

**Approval Queue as Fallback**: Every write lands in approval queue before execution, providing human safety net.

### Extensibility: Plugin System + Custom MCP Tools

**Plugin Authoring**:
  - Manifest schema for scaffolding new MCP tool plugins
  - Community recipe marketplace planned (Q3 2026)
  - Users can load custom plugins without modifying core

**MCP Tool Organization** (20+ categories):
  - Code intelligence: LSP navigation, diagnostics, refactoring, type awareness
  - Version control: git operations, GitHub PR management
  - Execution: terminal commands, debugger integration, test orchestration
  - File ops: creation, deletion, search, tree traversal
  - Quality assurance: linting, formatting, coverage, security audits

## OPERATIONAL CAPABILITIES ASSESSMENT

### Multi-Persona Workflows: ⚠️ WEAK FIT
**Thunderbird Need**: Hale (COS) → A1 (Intake) → A8 (Experience) → Dani (Client Concierge). Sequential handoff with different personas taking different roles.

**Patchwork OS Capability**:
  - IDE Bridge is single-agent-centric (Claude, GPT, etc., but one model per recipe)
  - YAML recipes define trigger-action, not multi-persona workflows
  - No built-in persona abstraction (no staff roles, no memory layers)
  - Could spawn different Claude "personas" via subprocess prompt variation, but:
    - No explicit handoff mechanism between recipe runs
    - No persona-specific memory or context preservation
    - State passed via handoff-note.json, not persona profiles

**Verdict**: Possible workaround (craft personas via prompt + persona file hooks), but not native to Patchwork design.

### Long-Running Processes (90+ Day Client Journeys): ⚠️ MODERATE FIT
**Thunderbird Need**: Track client state across Kuklinski (16 TPs, 8+ months), Loucks (22 TPs, 8+ months), McLeod (27 TPs, 8+ months).

**Patchwork OS Capability**:
  - Handoff-note.json holds 10 KB of state per session
  - Decision trace logs persist indefinitely (JSONL)
  - No explicit "booking lifecycle" tracking (domain-specific to travel)
  - Recipes are event-driven (git commit, test failure, cron)—not client-event-driven
  - Could repurpose cron recipes (daily check-in, weekly review) to simulate lifecycle, but requires manual dossier sync

**Verdict**: Plausible for operational tracking via cron recipes + trace logs, but Patchwork OS not designed for business domain state (e.g., "client is in phase 2 of booking lifecycle").

### State Persistence (Dossier ↔ Booking ↔ Mission Board): 🟡 MODERATE FIT
**Thunderbird Need**: dossier.json ↔ booking Google Sheet ↔ mission_board.json ↔ email drafts. File-based state sync.

**Patchwork OS Capability**:
  - Handoff-note.json (10 KB shared state per session)
  - Decision trace logs (JSONL, unlimited)
  - HTTP endpoints for external integrations (webhooks, push notifications)
  - `contextBundle` for parallel state fetch
  - No built-in sync to external systems (Google Sheets, email, Slack)—but MCP tools can call HTTP endpoints

**Verdict**: Could extend handoff-note.json to hold dossier snippets + trace logs for booking changes, but no native sync to sheets/email/mission-board. Would require custom MCP tools.

### Real-Time Visibility (COS Seeing What's In Flight): 🟡 MODERATE FIT
**Thunderbird Need**: Hale sees all active tasks, agent status, approvals pending, error states. Status bar + logs.

**Patchwork OS Capability**:
  - Web dashboard at `localhost:3100` shows:
    - Pending approvals (approval queue)
    - Live sessions (currently running recipes)
    - Recipe run history
  - Mobile PWA for push-based approvals
  - `getBridgeStatus` tool exposes fallback paths + connection state
  - Activity logs, diagnostics watchers (configurable cap 10-50 entries)

**Verdict**: Dashboard is real-time within IDE context, but not Thunderbird-aware. Would need custom integration to surface Thunderbird's mission board + client workflows into Patchwork dashboard.

### Cost-Aware Routing (Prefer Cheaper Models): ✅ GOOD FIT
**Thunderbird Need**: Route expensive work to Claude, routine work to DeepSeek V3.1, simple tasks to Gemini Flash.

**Patchwork OS Capability**:
  - `--claude-driver` flag: Claude (default), Gemini, OpenAI GPT, Grok, Ollama
  - Each recipe specifies `model: "claude-sonnet-4.6"` or swaps to GPT/Gemini/Grok
  - Mixed-model workflows within automation chains (recipe A → Claude, recipe B → Gemini)
  - Default models: Claude Sonnet 4.6, Gemini 2.5-Flash, GPT-4o, etc.
  - No cost-tracking built in (would need external monitoring)

**Verdict**: Excellent for model routing by recipe. Requires external cost monitoring (e.g., `rtk gain` or custom telemetry).

### Async/Background Task Handling: ✅ GOOD FIT
**Thunderbird Need**: Spawn Haiku headless tasks without blocking main loop. Stdout/stderr to log file.

**Patchwork OS Capability**:
  - Subprocess agent spawning natively supported
  - Flag: `--automation --automation-policy <path.json> --claude-driver subprocess`
  - Recipe automation hooks: `onGitCommit`, `onTestRun`, `onDiagnosticsError`, etc.
  - Approval queue doesn't block recipe execution (fire-and-forget webhooks + push notifications)
  - No explicit process detachment guidance (assumes `nohup` or systemd)

**Verdict**: Supports background tasks, but less prescriptive than Thunderbird's subprocess.Popen pattern. Would need custom wrapper (similar to thunderbird_headless_spawn.py).

### Error Recovery (Retry, Escalation): 🟡 MODERATE FIT
**Thunderbird Need**: OpenCode fails → retry once → escalate to Claude Code.

**Patchwork OS Capability**:
  - Fallback patterns for IDE-extension tools (degrade to CLI)
  - Approval queue catches failed writes
  - Conditional triggers via `AutomationCondition` can branch on error states
  - No built-in retry logic (recipes either succeed or land in approval queue)
  - No escalation chain (would need to craft recipes chaining to different models)

**Verdict**: Approval queue is a safety net, but no explicit retry/escalation. Could extend with custom automation hooks.

## DIRECT THUNDERBIRD APPLICABILITY

### Strongest Fit Areas

**1. Approval Queue Pattern (WF-17 Draft Gate)**
   - Patchwork's approval queue (`~/.patchwork/inbox/`) is conceptually identical to Thunderbird's WF-17
   - Every consequential action awaits human approval via web UI or mobile PWA
   - Could replace WF-17 infrastructure if recipes were crafted to emit draft emails

**2. Recipe Triggers + Automation Hooks**
   - YAML recipes elegantly model Thunderbird's event-driven workflows:
     - Client inquiry received (git event, HTTP webhook) → A3 Dani replies
     - Booking confirmed (cron daily check) → A8 Atlas creates recommendation
     - Payment due (cron weekly check) → A9 Vic sends invoice reminder
   - Automation hooks (`onGitCommit`, `onRecipeSave`, `onDiagnosticsError`) could map to Thunderbird events

**3. Multi-Model Support + Cost Awareness**
   - Recipe-level model selection aligns with Thunderbird's cost guardrails
   - Could tier recipes: routine tasks → DeepSeek, complex analysis → Claude, simple → Gemini
   - Solves current challenge of routing decisions spread across keyword_router.py + COS judgment

**4. Error Recovery via Fallback + Approval Gate**
   - Approval queue catches errors before they reach clients (WF-17 gate)
   - Fallback patterns prevent silent failures (explicit reconnect instructions)

---

### Moderate Fit Areas

**1. State Handoff via Handoff-Note**
   - 10 KB handoff-note.json could carry dossier snippets between recipe runs
   - Decision traces (JSONL) could log all booking changes (similar to mission board commits)
   - Would require custom serialization (dossier → JSON → handoff-note ↔ mission board sync)

**2. Real-Time Dashboard**
   - Patchwork's web UI at `localhost:3100` shows pending approvals + live sessions
   - Could extend to display Thunderbird's mission board + client radar
   - Mobile PWA for approvals is valuable for Hale's oversight

**3. Integration with External Tools**
   - HTTP endpoints + webhooks enable push-to-Google-Sheets, Telegram notifications
   - Could replace OpsCenter/thunderbird_telegram_gw.py with Patchwork webhook triggers

---

### Weak Fit Areas

**1. Multi-Persona Staffing Model**
   - Patchwork OS is fundamentally single-agent-per-recipe (though multiple recipes can run sequentially)
   - Persona abstraction in Thunderbird (Hale has 24 memory layers; A1-A9 are specialized roles) is not native to Patchwork
   - Would require encoding personas as prompt instructions + custom memory files, losing explicit role abstraction

**2. Business Domain State Management**
   - Patchwork OS assumes code/IDE domain (LSP navigation, diagnostics, git)
   - Thunderbird operates on travel domain (bookings, commissions, customer preferences)
   - Handoff-note.json could carry dossiers, but traces/history would lack domain semantics

**3. Keyword Router Logic**
   - Thunderbird's keyword router (23+ keywords → Claude) is compact and specialized
   - Patchwork's YAML recipes are more verbose but more flexible
   - Net: Patchwork could replace it, but with more boilerplate

**4. Telegram C2 Command Dispatch**
   - Patchwork has HTTP webhooks, not native Telegram integration
   - Would require custom Telegram → HTTP bridge (additional component)

## ARCHITECTURAL COMPARISON

### Current Thunderbird Orchestration Stack

**Component 1: Keyword Router** (`OpsCenter/keyword_router.py`)
- Input: Task name or description
- Logic: 23+ keywords match to Claude (default) or other routing
- Output: Model selection + persona assignment
- Pain point: Routing scattered across multiple files; hard-coded keywords; no cost awareness

**Component 2: Persona Memory System** (24 files, `Personas/`, `~/.claude/projects/*/memory/`)
- Input: Persona name (Hale, A1, A3, etc.)
- Logic: Read persona file + memory layers + context
- Output: Prompt preamble + context
- Pain point: Manual context assembly; no native handoff between personas; 24 memory files to maintain

**Component 3: Shared State Files** (JSON-based)
- dossier.json (per client)
- mission_board.json (tasks)
- hale_state.json (COS state)
- session_autosave_latest.md (session checkpoint)
- Pain point: No atomic transactions; manual sync between files; race conditions possible

**Component 4: Telegram C2** (`OpsCenter/thunderbird_telegram_gw.py`)
- Input: Telegram command from COS
- Logic: Command parsing, paging logic
- Output: Agent spawn or state update
- Pain point: Single point of failure; not integrated with task queue

**Component 5: Email Workflows** (WF-17)
- Input: Draft email in Gmail `Label_Commander-Review`
- Logic: COS reviews, approves, auto-sends
- Output: Email to client or supplier
- Pain point: Manual gate; no error recovery; lost context between drafts

**Component 6: Headless Claude Spawning** (`OpsCenter/*headless*.py`)
- Input: Task description + environment
- Logic: Verify daemon status, inject token, spawn subprocess
- Output: Log file with agent output
- Pain point: Multiple spawn wrappers; error handling inconsistent; no retry logic

### Head-to-Head: Key Capabilities

**Approval Gate (WF-17 vs Patchwork Queue)**
- **Thunderbird WF-17**: Gmail Label_Commander-Review → COS review in `/drafts` → auto-send
  - Pro: Email-native, integrated with existing workflow
  - Con: Manual gate, no error recovery, lost context between reviews
- **Patchwork Approval Queue**: Every write lands in `~/.patchwork/inbox/` → web UI or mobile approval
  - Pro: Atomic, approval rate-limited by human decision, mobile-friendly
  - Con: Not email-integrated, requires web UI click (slower for COS on mobile)
- **Verdict**: Patchwork's queue is more robust; Thunderbird's email integration is faster for Yoda

**Multi-Agent Coordination (A1 → A8 → Dani vs Sequential Recipes)**
- **Thunderbird**: Manual choreography via Hale; explicit persona memory at each step
  - Pro: Clear role separation, specialized context per persona
  - Con: Hale bottleneck, manual context assembly, hard to parallelize
- **Patchwork**: YAML recipes chain sequentially; handoff-note.json passes state
  - Pro: Decoupled from Hale, no coordinator bottleneck, recipes can run in parallel
  - Con: No native persona abstraction, prompts must encode roles
- **Verdict**: Patchwork decouples better; Thunderbird's explicit roles are clearer

**Cost-Aware Routing**
- **Thunderbird**: Keyword router + human judgment + per-task config (fragmented)
- **Patchwork**: Recipe-level `model` field + `--claude-driver` (systematic)
- **Verdict**: Patchwork's model selection is more orderly

**Long-Running Client Journeys (90+ days)**
- **Thunderbird**: Dossier + mission board + session autosave (explicit domain semantics)
- **Patchwork**: Handoff-note (10 KB) + traces (unlimited) (generic state)
- **Verdict**: Thunderbird's dossier is more semantically rich; Patchwork's traces provide audit trail

## INTEGRATION COMPLEXITY

### Effort to Integrate: **MEDIUM-TO-HIGH** (4-8 weeks)

**Why Medium**:
  - Patchwork OS ships all pieces (bridge, recipes, dashboard)
  - Both use WebSocket/MCP, so tool integration is straightforward
  - No database dependency (both file-based state)

**Why High**:
  - Thunderbird's persona model (24 files + memory layers) doesn't map 1:1 to YAML recipes
  - Business domain (travel bookings, commissions) requires custom MCP tools in Patchwork
  - Telegram C2 dispatch would need custom bridge (Telegram → HTTP → Patchwork)
  - Existing workflows (WF-17, keyword router, dossier sync) must be refactored or run parallel

### Breaking Changes: **YES** (significant refactoring required)

- Persona routing changes from keyword-based to YAML recipe-based
- Email workflows change from Gmail WF-17 to Patchwork approval queue
- State handoff changes from explicit persona context to generic JSON
- Dossier sync changes from mission_board.json to handoff-note.json + traces

### Parallel Run Feasibility: **YES** (but complex)

- Could run Patchwork recipes alongside existing Thunderbird infrastructure
- Risk: state divergence if both systems update dossiers or mission board
- Transition strategy: Run in "read-only" mode for 2-4 weeks, then flip writes to Patchwork

### Team Learning Curve: **MEDIUM** (2-3 weeks for Hale + A-staff)

- Learn YAML recipe syntax (2 days)
- Understand handoff-note.json vs persona files (2 days)
- Learn approval queue mechanics (1 day)
- Refactor existing workflows into recipes (1-2 weeks)
- Thunderbird domain expertise (Hale + A-staff) stays the same—just new tooling

### Deployment: **LOCAL** (no cloud required)

- Patchwork OS runs as Node.js daemon (systemd unit)
- Headless operation: `patchwork --automation --automation-policy <path.json>`
- VPS deployment supported but not necessary for Thunderbird (Yoga is local)
- No vendor lock-in (MIT licensed, fully open-source)

### Platform Support: **LINUX** ✅ (and macOS/Windows)

- Yoga runs openSUSE Tumbleweed (Linux) — Patchwork OS fully supported
- Fallback tools (tsc, eslint, etc.) available on Linux
- systemd integration native to Linux

### Credential Handling: **EXCELLENT SUPPORT**

- OAuth token injection via environment (same as Thunderbird's pattern)
- CLI auth: `claude auth login` (default Claude)
- API key auth: `gemini auth login` or environment vars (GPT, Grok)
- Token refresh daemon integration (Patchwork has mechanism; Thunderbird has separate daemon)
- Mobile approvals use single-use 256-bit tokens (timing-safe)

### Claude Code Integration: **SEAMLESS**

- Patchwork OS is a superset of Claude IDE Bridge
- Claude Code CLI speaks MCP JSON-RPC 2.0 (native to Patchwork)
- Can spawn Claude Code subprocess tasks via `--claude-driver subprocess`
- Headless Claude (like Thunderbird's headless dispatches) integrates natively
- Token caching + context compaction hooks supported in bridge

## STRATEGIC RECOMMENDATION

### Relevance Score: **6.5/10**

**Justification**:
- **Strong for**: Approval queue pattern, recipe-based event dispatch, cost-aware multi-model routing
- **Moderate for**: State handoff between agents, real-time dashboard, error recovery
- **Weak for**: Multi-persona staffing model, travel domain semantics, Telegram C2 integration
- **Not for**: IDE-centric tool set (Patchwork optimized for code navigation/git; Thunderbird needs booking/pricing/supplier tools)

### Implementation Priority: **MEDIUM** (not urgent, but strategic)

**Rationale**:
- Thunderbird's current orchestration works but is fragmented (5-6 loose components)
- Patchwork OS would consolidate 2-3 components (keyword router, WF-17, headless spawning)
- ROI: cleaner codebase + cost tracking + error recovery, but not a revenue driver
- Risk: refactoring effort diverts from client booking work (90-120 day booking cycles)

### Recommended Action: **SELECTIVE ADOPTION** (start with recipes for cron-based workflows)

**Rationale**:
- Full Patchwork replacement would require 4-8 weeks
- Selective adoption: deploy Patchwork for low-risk automation (cron recipes, report generation)
- Keeps WF-17 + keyword router intact until Patchwork recipes prove reliable
- Reduces risk and allows team to learn YAML recipe syntax gradually

## RISKS & CONCERNS

### Technical Risks: **MEDIUM**

**Risk 1: State Divergence During Parallel Run**
- If WF-17 and Patchwork approval queue both run, dossiers/mission_board could diverge
- Mitigation: Run Patchwork read-only for 2-4 weeks before flipping writes

**Risk 2: Handoff-Note 10 KB Cap**
- Large dossiers (clients with 90+ day booking history) might exceed 10 KB
- Mitigation: Store full dossier in mission_board.json; handoff-note holds only deltas

**Risk 3: Recipe YAML Complexity**
- 23+ recipes could become hard to maintain (no IDE support for recipe syntax)
- Mitigation: Template generator or recipe builder UI (can extend Patchwork dashboard)

**Risk 4: Approval Queue as Bottleneck**
- If COS is offline or slow to approve, tasks queue up
- Mitigation: Set approval SLA (e.g., 5 min for drafts, 30 min for routine tasks); escalate to A12 ELON if pending

### Unique Value of Patchwork OS

1. **IDE-first design**: Unlike LangGraph/CrewAI/Temporal (CLI/API-first), Patchwork is tightly integrated with VS Code/JetBrains—enables human-in-the-loop within familiar environment
2. **Approval gate**: Only Patchwork has native approval queue (LangGraph, CrewAI, Temporal all require custom implementation)
3. **Local-first**: Unlike Prefect/Temporal (cloud-first), Patchwork runs entirely on user machine—no vendor lock-in
4. **Multi-model support**: Recipe-level model selection (Claude, GPT, Gemini, Grok, Ollama) out of box—others require wrapper code
5. **Fallback patterns**: Graceful degradation when IDE extension disconnects (unique to IDE-first design)

- **Claude Usage Monitor** (cost tracking): Patchwork doesn't track costs; monitor could parse Patchwork logs
- **Thunderbird's existing MCP tools** (120+ tools): Patchwork recipes can invoke them via MCP client
