## VERDICT

**Rethink the shape, keep the diagnosis.** The design's read of the failure mode is correct — enforcement must live in structure, not memory — but v2 as drafted answers that correctly-stated problem with the wrong-sized solution: a new SQLite database, a full OTel span tree, a 14-code taxonomy, and a TUI dashboard, built on top of a hook-enforcement claim (`SubagentStart`) that **does not currently exist in this environment's configuration** and has never been tested. Meanwhile the cheapest, highest-leverage fixes — identified by the design's own audit — are single-file changes to code that is *already wired and already running*, and one of those already-running files is caught red-handed doing the exact "silence read as green" thing the design spends a whole section (§11) warning against. Ship the minimum viable spine (below) this week. Defer SQLite, the span tree, the 14-code MAST enum, and the TUI dashboard until there is enough real traffic to need them — at 4 rows in the ledger that has been born, none of that infrastructure has anything to index yet.

### F4. `verify_and_record()` still has zero production callers — confirmed independently, right now
Re-ran the audit's grep myself: `verify_and_record(` appears only in `tests/test_delegation_outcomes.py` (3 call sites), never in a non-test file. The single named enforcement point for SO 2026-07-19 (CC Integrity Double-Check) is unenforced at the moment this review was written. The design proposes fixing this via a `Stop` hook (§9). Two problems with that specific fix:

1. **Stop hook contention/ordering, unaudited.** `Stop` already has 2 handlers at project scope + 5 at user scope = 7 handlers firing on every stop event (`claudekit-hooks create-checkpoint`, `post_stop_retro.sh`, `keyword-router-checkpoint.sh`, `session_stop.sh`, `post_stop_hale_bus.sh`, `post_stop_git_check.sh`, `detect_max_exhaustion.sh`). Claude Code hook arrays run in listed order (documented behavior); adding an 8th that calls `verify_and_record()` — which itself dispatches to a different engine (AG or OC) over a real subprocess/network round-trip, `contact_ag.py`-style, measured in this system at multi-minute latency for real prompts — means **every single Stop event on every session now blocks on a cross-engine call** unless explicitly scoped to top-level "done" claims only. The design doesn't specify that scoping.
2. **Recursion risk, unaddressed.** `SubagentStop` already triggers `create-checkpoint`. If a future `Stop`/`SubagentStop` hook triggers `verify_and_record()`, and `verify_and_record()`'s own cross-engine dispatch itself produces tool calls or nested subagent stops (plausible — AG's own turn ends with a Stop-equivalent), you have a hook invoking work that re-triggers the same hook class. The design needs an explicit re-entrancy guard (e.g., a `phase` check that only fires on `phase in ("certify","close")`, not on every raw Stop) before this is safe to wire in as a blanket hook.

**Lower-blast-radius alternative, and the one I'd actually ship**: the audit's own fix #1(b) — make `certify_mission_and_record()` / `close_sss()` require a `verify_and_record()` call for CC-self-executed work the same way they already require cross-seat certification for delegated work. That's a code-level gate inside an already-tested, already-called function (`certify_mission_and_record()`, `core/relay/delegation_wiring.py:253`), not a new hook event with unscoped blast radius across every tool call in every session.

### F5. Dual-write (SQLite + JSONL mirror) trades a proven durability pattern for an unproven one, for no volume that needs it
`core/staffing/delegation_outcomes.py:91-101` — the actual current write path — is a single `fcntl.flock`-guarded, `os.fsync`-forced JSONL append. This is already crash-safe: a process dying mid-write leaves either a complete line or nothing (the flock+fsync pair is exactly the right primitive for this). The design proposes adding `OpsCenter/wing_spans.db` (SQLite) as primary, "keep an append-only JSONL mirror... so nothing that works today breaks" (§2). That is **dual-write**: every span-producing code path must now succeed at two independent I/O operations, with no described transaction boundary, no described reconciliation job, and no described behavior for "SQLite write succeeded, JSONL write failed" (or vice versa) — drift between the two stores is silent until someone notices the joins disagree.

At current volumes — `delegation_outcomes.jsonl` (4 lines), `silver_ledger.jsonl` (3,115 lines), `seat_scorecard.jsonl` (87 lines) — a `sqlite3`/DuckDB **read-time join** across the existing JSONL files by `ticket_id`/`mission_id` (which the audit confirms all already share) fully satisfies "no single query stitches these together" (the design's own stated gap, §1 row 1) without a second write path. SQLite as a *query engine over the existing files* (attach, or load-then-query on demand) is a good idea. SQLite as a *second source of truth requiring dual-write discipline* is not justified until row counts are in the hundreds of thousands, not low thousands.

## SERIOUS

### S1. `pass^k` is not measurable at this system's volume, and the design ships without answering its own open question
Design §13 Q3 asks this and leaves it open; §10 nonetheless specifies `pass^k` as a scorecard metric to build. `pass^k` requires running the *identical* task *k* independent times (τ²-bench's definition, cited correctly in the SOTA doc). This system dispatches a handful of real, unique, non-repeatable tasks per day ("email the client," "scrape this booking") — there is no way to run the same real task 4 times without either (a) fabricating synthetic repeats that aren't the real work, or (b) waiting years to accumulate 4 *naturally recurring* instances of the same task type, by which time the underlying models/prompts have already changed underneath the metric.

**Answer to the design's own open question:** no, not measurable as literally specified. The right substitute for irreplaceable day-to-day work is the **three-valued Pass/Fail/Inconclusive verdict** (AgentAssay pattern, already surfaced in the SOTA docs' own recommendations) rolled up into a **rolling failure rate with a confidence interval that widens honestly at low n** (a Wilson interval on 4 data points should visibly say "wide," not collapse to a false-precision percentage) — not a repeated-trial metric this system cannot generate. Keep `pass^k` only for the SOTA docs' own separate suggestion: a *monthly* synthetic replay of 3–5 canonical mission types, run 3x each across CC/OC/AG — that is a real, buildable pass^k, but it is a once-a-month calibration exercise, not a per-task production metric, and the design conflates the two.

### S2. Cross-engine verification by a structurally weaker model is not verification of CC's judgment work — the design doesn't distinguish where it's valid
This is the single most important question the tasking asked, and the design draft doesn't actually answer it — it asserts the pattern is "architecturally sound per the literature" (true) without addressing the specific failure mode the Commander's own two named incidents demonstrate: AG's Flash tier (the *weak* fallback, not the default Gemini 3.1 Pro) dropped a state, and AG returned a citation-free report the same morning this review was requested. Both incidents show the verifying/reporting engine underperforming, not the engine being verified.

The resolution is in the design's own §5 tiering, but the design doesn't apply it to §9's blanket claim: **Tier 1 (deterministic: does the file exist, did the test pass, did the URL 200) is valid cross-engine verification regardless of which engine runs the check** — a weak model asking "does this path exist" is just as reliable as a strong one, because the check doesn't route through the verifier's own judgment. **Tier 2 (LLM-judge open-ended quality/reasoning judgment) is NOT valid when the judge is systematically weaker than the author on the dimension being judged.** Routing CC's client-voice prose or strategic reasoning through OC (DeepSeek, the JET/mechanical-tier default) or AG-Flash for a substantive judgment call doesn't remove self-preference bias — it substitutes it for a competence-mismatch bias, where a weak judge's PASS is false confidence (it didn't understand the work well enough to catch a real flaw) and its DISCREPANCY is often a false alarm (it flagged something CC did correctly but the judge model doesn't have the context to recognize as correct). Neither is "verification" in the sense the Commander is asking for.

**Concrete fix the design should adopt explicitly:** bind `verify_and_record()`'s mandatory-cross-engine-check requirement to **Tier-1 ground-truth claims only** (did the artifact get created, does the commit exist, did the email actually send) for every seat including CC. Reserve **Tier-2 judgment calls on CC's own high-judgment work** (client voice, strategy, architecture) for either (a) Commander spot-check, explicitly labeled calibration-only per the design's own §5.3, or (b) a same-or-stronger-tier engine if one becomes available — never route a substantive CC judgment call through OC/AG-Flash and record its verdict as equivalent evidence to a Tier-1 check. Doing so today would generate exactly the false-confidence-and-false-alarm outcome axis 6 of the tasking asked about.

### S3. No cost estimate anywhere in the design, against a halved $100/mo Sonnet budget, with a plausible per-subagent cost multiplier
The design never estimates token/dollar overhead. Two concrete risks: (a) if `verify_and_record()` gets bound to `SubagentStop` (fired per-subagent, not just per top-level mission — see F4), the cross-engine dispatch cost multiplies by subagent count, not by mission count, which could be 5–20× more cross-engine calls/day than the Commander's actual task volume justifies; (b) Tier-2 LLM-judge calls plus deterministic checks plus the "brutal weekly appraisal" (§11, itself run "by a different model family") are all new recurring token spend with no budget line. **Fix:** scope every new automatic verification trigger to top-level mission close only (not every subagent stop), and add a cost field to `delegation_outcomes` rows (SOTA doc's own recommendation) before adding more callers, so the very first week of real data answers "does this cost more than the work it oversees" with a number instead of a guess.

### S4. NIH-adjacent middle path: right call on Langfuse/Phoenix, wrong call on building a bespoke span database instead
§12 is correct to defer self-hosting Langfuse/Phoenix — a Postgres+ClickHouse+Redis Docker stack is a real ops burden for a solo operator 11 days after decommissioning a custom web app for being unmaintainable (CLAUDE.md, 2026-07-18 entry). But the design's alternative — hand-build a span tree, a reaper, a lease system, and a scorecard in SQLite — is still building a smaller, worse version of the same category of system, just without the vendor. Given existing systemd+Python competence and near-zero current volume, the right-sized move is: adopt the `gen_ai.*` **field names** on the existing flat JSONL rows (free, no schema migration, satisfies "portable later" per the SOTA doc), and wire the **already-built, already-audited** heartbeat scripts (`scripts/hale_heartbeat_scan.py`, `core/watchtower/thunderbird_heartbeat.py` — confirmed to exist per the audit, not newly built) into `record_outcome()` for lost-task detection, instead of standing up a new reaper/lease subsystem from scratch. Revisit Langfuse/Phoenix/a real span DB only when there's enough volume that a read-time JSONL join actually gets slow — nothing in this system is close to that today.

## AXIS-BY-AXIS

**1. Orphan risk.** `SubagentStart` is not configured anywhere and its firing under the Teams experimental flag is unverified (F1). `UserPromptSubmit` is already occupied at user scope and explicitly zeroed at project scope (F2) — "gets a caller for free" is wrong; it's a real wiring task with an unresolved merge-semantics question. `PreToolUse`/`PostToolUse` do exist and do fire on every tool call (verified: `hooks/pretooluse_policy.py`, fail-closed; `hooks/posttooluse_audit.py`, best-effort) — those two claims hold. `Stop`/`SubagentStop` exist but are already crowded (7 handlers) and none currently touch spans or verification (F4). **v2 becomes orphan #7 the moment any of its "non-optional triggers" turns out to be the unverified `SubagentStart` claim, or the moment the SQLite mirror write path silently starts failing while the JSONL mirror keeps working and nobody notices the drift (F5).**

**2. Hook enforcement blast radius.** `pretooluse_policy.py` is deliberately fail-closed by design and is already careful about it (single `sys.exit`, outermost `except BaseException`, audit-log write wrapped in its own try so a logging failure can't flip the gate open) — that posture is correct for a policy gate whose job is to deny. It is the **wrong** posture to copy for a new verification hook: a `verify_and_record()`-calling `Stop` hook that fails closed on a hung cross-engine call would block session termination indefinitely, a materially worse outcome than the current no-op. Latency: every Bash/Edit/Write/browser/Gmail call already pays a `python3` subprocess spawn today (pre-existing cost, not new) — the new cost is the second-order one from F4/S3 (cross-engine dispatch cost triggered from a hook, at unscoped frequency). Recursion: real risk, not addressed anywhere in the draft (F4.2).

**3. Storage migration.** Traced: both brief engines read `wing_ops_report.build_wing_ops_digest()` → `delegation_outcomes.rollup_stats()` → `_read_rows()` (plain JSONL parse, `core/staffing/delegation_outcomes.py:162`) and `silver.scorecard.summary()`. Nothing currently touches SQLite for these two paths. Dual-write is the wrong call at this volume (F5) — a read-time join is sufficient and doesn't introduce a second failure mode. If SQLite is adopted anyway, it should be a **derived, rebuildable-from-JSONL index**, never the primary write target, so a corrupt/lost `.db` file is a `rm` + rebuild, not data loss.

**4. Metric validity at low volume.** Not measurable as `pass^k` literally specified (S1). Right answer: three-valued verdicts + rolling failure rate for daily irreplaceable work; a monthly synthetic pass^k-style replay of canonical mission types for calibration only, kept explicitly separate from the daily ledger.

**5. NIH.** Right to defer Langfuse/Phoenix; wrong to build a bespoke SQLite span/lease/reaper system as the substitute — reuse the already-built heartbeat scripts instead of building a new detection subsystem (S4).

**6. The verification recursion problem — the most important question.** Cross-engine verification by a weaker model is legitimate for Tier-1 ground-truth checks and is theater (false confidence in one direction, false alarms in the other) for Tier-2 judgment calls on CC's own high-judgment work. The design needs to say this explicitly and bind `verify_and_record()`'s mandatory trigger accordingly (S2) — right now it implies uniform cross-engine verification is always the fix, which is not true for the two incidents actually cited as its justification (one was Flash's own Tier-1-checkable state drop; grading *that* cross-engine was correct. Grading CC's *own* prose/strategy work through OC/AG-Flash would not be).

**7. Cost.** Unestimated anywhere in the draft (S3). The realistic risk isn't the deterministic tier (free) or occasional judge calls (pennies) — it's an unscoped hook trigger multiplying cross-engine dispatch calls by subagent count instead of mission count.

**8. What's missing.** Retention/rotation (F6, concretely verified as already broken for two files), secrets/PII in transcripts (F7, concretely tied to a real incident from this same week), a cost field, and an explicit statement of what happens when the Commander disagrees with a verdict (nowhere in the draft — `DISCREPANCY`/`BLOCKED` verdicts page the Commander per `delegation_outcomes.page_commander()`, but there is no described path for "Commander overrides a DISCREPANCY verdict as a false alarm" other than presumably editing the JSONL by hand, which is not durable or auditable). Recovery after a crash mid-delegation is partially covered by the existing fcntl+fsync JSONL pattern (good) but not by the proposed SQLite mirror (F5). What happens while the operator is asleep is implicitly "the existing paging lane," which is fine, but the design doesn't say so explicitly — worth stating rather than assuming.

## MINIMUM VIABLE SPINE (if only ~20% gets built)

In this order — each step is a single-file or near-single-file change to code that is *already wired and already running*, no new hook events, no new database, no new taxonomy, no new dashboard:

Ships in under an hour, fixes something actively mailed to the Commander twice daily today. Do this before anything else — everything downstream of this file is currently lying by omission.

2. **Give the oldest dead function a caller.** `directive_ledger.capture()` has been frozen 10 days. Wire it into the existing `UserPromptSubmit` chain — but first resolve F2's merge-semantics question empirically (does project-level `[]` suppress user-level hooks, or do both fire?), then add the call to whichever scope actually governs this session.
