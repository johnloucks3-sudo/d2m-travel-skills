MECHANISM — confirmed: Restart=always + M-153 dead-thread exit = self-fueling loop.

  main() at L2722–2733: while True, every 30s checks if any bot thread is dead.
  If dead: os._exit(1) (L2732). systemd sees exit → Restart=always → sends SIGTERM
  to stop (if process hasn't already gone), starts new one. New one starts all
  poll threads fresh. This is INTENTIONAL design (M-153), and is working correctly
  for crash recovery. The "Failed with result 'exit-code'" is systemd correctly
  classifying a non-zero exit as failure. The Restart=always means it immediately
  re-launches, so there is no actual service outage — just noise in the unit state.

THE BUG: os._exit(1) exits with code 1 → systemd marks it 'exit-code' FAILED →
triggers OnFailure=thunderbird-generic-remediate@%N.service. That remediate
handler then ALSO potentially issues a restart — double restart source during
the crash window. The 17:37 → 17:50 sequence (13-minute gap) is consistent with
the remediate handler delaying before restarting.

FIX A:
  Option 1 (preferred — minimal change): Change os._exit(1) at L2732 to
  os._exit(0). Exiting with code 0 still triggers Restart=always (which restarts
  on ANY exit) but does NOT mark the unit as 'exit-code' FAILED, suppresses
  OnFailure trigger, and stops the false-positive alert cascade.

  File: OpsCenter/thunderbird_telegram_gw.py
  Line: 2732
  Current:  os._exit(1)
  Change:   os._exit(0)

  Option 2: Add SuccessExitStatus=1 to the .service unit [Service] stanza.
  systemd then treats exit code 1 as a clean exit, suppressing 'exit-code' FAILED.
  No code change required. Minimal risk.

  File: ~/.config/systemd/user/thunderbird-telegram-gw.service
  Add to [Service]: SuccessExitStatus=1

  OPINION: Option 1 is cleaner — exit 0 is semantically correct for a planned
  restart (not a crash). Option 2 is lower-risk for a one-line unit change.
  Either alone fixes the FAILED/OnFailure noise. Both are valid.

  What NOT to do: Remove M-153 logic. It correctly restarts the process when a
  bot thread dies silently. The design is sound; just the exit code is wrong.

3. FIX B — SINGLE-POLLER GUARD (getUpdates Conflict)
═══════════════════════════════════════════════════════════

CONFIRMED: Only ONE process (PID 2137) is running thunderbird_telegram_gw.py now.
The conflict at 01:00:03–01:00:29 (×8 warnings, 2 tokens × 4 poll cycles each)
occurred while PID 2128 was alive. The watchdog at 00:56 attempted MCP restart
and the system went RED. No second gw process was spawned.

ACTUAL CAUSE of the 01:00 conflict: startup overlap window.

When systemd does Restart=always: old process gets SIGTERM → takes up to TimeoutStopSec
(default 90s) to die → new process starts. If SIGTERM doesn't immediately kill the
old process (it's blocked in a requests.post / SSL read as shown in the death_diag
stack trace), BOTH old and new are alive and polling for a window. At 01:00, the old
process (pid 2128, started 21:02) and a new one were briefly both alive.

The death log stack trace shows EXACTLY this: at time of SIGTERM, both bot threads
(D2MC2C + Dani) are blocked inside ssl.py read() inside getUpdates. The SIGTERM
fires in the main thread (time.sleep(30)), handler logs death and calls sys.exit(128+15),
but the daemon threads are blocked on network I/O — Python can't interrupt them
immediately. The new process starts, begins polling the SAME tokens → Telegram
sees two getUpdates → sends Conflict to both.

FIX B — two-layer fix:

  Layer 1 (source guard — minimal code change): Add a PID lockfile at process
  startup that blocks a new instance if an old one is still holding the lock.
  stdlib only (fcntl already imported at L208).

  File: OpsCenter/thunderbird_telegram_gw.py
  Insert after imports, before main() call (around L2810, after signal setup):

  --- DIFF ---
  +import fcntl as _fcntl_lock
  +_GW_LOCKFILE = Path("/home/john/Thunderbird/logs/telegram_gw.lock")
  +
  +def _acquire_instance_lock():
  +    """Block until any prior instance releases its lock. Non-blocking check
  +    with a 30s wait — if prior process is hung, TimeoutStopSec kills it."""
  +    fh = open(_GW_LOCKFILE, "w")
  +    try:
  +        _fcntl_lock.flock(fh, _fcntl_lock.LOCK_EX | _fcntl_lock.LOCK_NB)
  +    except BlockingIOError:
  +        log.warning("Another gateway instance holds the lock — waiting up to 30s")
  +        import select
  +        # Block until released (prior process exit releases flock automatically)
  +        _fcntl_lock.flock(fh, _fcntl_lock.LOCK_EX)
  +    fh.write(str(os.getpid()))
  +    fh.flush()
  +    return fh  # keep fh open (lock released on GC/close)
  +
  +_instance_lock_fh = _acquire_instance_lock()  # call before main()
  --- END DIFF ---

  NOTE: fcntl flocks are released automatically when the process exits (fd closed
  by kernel), so a SIGTERM-killed process releases immediately regardless of
  whether Python cleanup runs. This closes the overlap window cleanly.

  Layer 2 (unit config): Add TimeoutStopSec=15 to the service [Service] stanza.
  Forces systemd to send SIGKILL after 15s if the process doesn't exit cleanly.
  Prevents the 90s default overlap window.

  File: ~/.config/systemd/user/thunderbird-telegram-gw.service.d/resource-limits.conf
  Add: TimeoutStopSec=15

  OPINION: Layer 2 alone won't fully fix it (15s is still an overlap window);
  Layer 1 alone is sufficient but slow on hung instances. Both together are robust.

4. FIX C — NETWORK/SSL MITIGATION

  Telegram's long-poll model is idempotent: if getUpdates times out or resets,
  the offset is NOT advanced (confirmed: L2349–2354, backoff on exception,
  offset unchanged). Next successful poll retrieves the same updates. The only
  risk is a message delay equal to the backoff duration (starts at 5s, max 60s).
  Messages are NOT dropped; they queue server-side for 24h.

  Send failures (tg_send) on network errors DO risk message loss — but the
  log shows these are getUpdates errors, not send errors.

CURRENT BEHAVIOR:
  tg_get_updates (L497–499): requests.post with timeout=35 (outer) and
  Telegram long-poll timeout=15 (inner, passed to API). The mismatch is harmless

  timeout on the long-held SSL connection (~17:19, cluster of 3 within 20s).

  SSLEOFError UNEXPECTED_EOF_WHILE_READING: SSL session terminated abruptly by
  server side (Telegram CDN/load balancer cycling). Recoverable.
