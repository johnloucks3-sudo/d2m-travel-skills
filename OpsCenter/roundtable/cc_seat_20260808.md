# CC SEAT — Round Table: Email C2/Tasking Redesign
**Hale-CC (Claude) · independent answer · 2026-08-08**

## PURPOSE
Answer the 5 Round Table questions on the canonical email C2 flow, grounded in
the actual code (not the brief's summary) — three of the five named files sit
under `OpsCenter/`, not the paths listed in the brief.

## BACKGROUND
Read the live code, not just the findings list:
- `core/comms/email_mode_classifier.py` — pure classifier, 3 modes only:
  **TASKING / FYI / CC**. No ACK mode exists.
- `core/comms/directive_executor.py` — `route_email()` dispatches by mode;
  `execute_directive()` gates any "done" claim behind
  `integrity_check.verify_and_record()` (cross-engine, SO 2026-07-19-compliant).
- `OpsCenter/mission_board_sync.py` `add_mission()` — already has the schema
  Q3 needs: `assigned_to` (WHO), `deadline_hours` (RDD), `acceptance_criteria`
  (ACTION), and — for cross-Hale delegations — `verification_artifact` /
  `certified_by` (DELIVERABLE + close-out). This schema does not need to be
  invented; it needs to be *used* by the email path.
- `core/relay/task_templates.py` — `build_ag_task` / `build_oc_task` /
  `build_cc_task` / `build_flash_task` / `build_haiku_task`, all gated by
  `core.silver.gate.is_checkable()`.

## FINDINGS (independent read of the code, beyond the brief's list)
1. **`route_email()` creates NO mission for FYI or CC** (`directive_executor.py:162-165`
   — `"FYI / CC: informational... no mission, no reply"`). This directly
   violates Commander non-negotiable #2 ("ack still logs/acks the task") and
   #1 (closed loop, every message) as written today.
2. **`_create_email_mission()` hardcodes `assigned_to="unassigned"`**
   (`directive_executor.py:105-129`). Even a TASKING-mode mission created
   from email never populates WHO. This is the single blocker on Q3 — the
   schema exists, the caller doesn't fill it.
3. **No ACK mode, no thread/ticket linkage.** The classifier judges every
   inbound message as a fresh TASKING/FYI/CC. It has no way to recognize "the
   Commander is closing a loop I (Hale) opened" vs. "the Commander is opening
   a new one" — those are structurally different events and need different
   handling, not a 4th classifier bucket.
4. `execute_directive()`'s verification gate is sound and already matches SO
   2026-07-19 — reuse it as-is, don't rebuild it.
5. `run_commander_directive_sweep.py` (per brief) still carries its own
   classify+reply logic in parallel with `email_mode_classifier.py` —
   "case-biased" — meaning two classifiers disagree today.

## DESIGN

**Q1 — Canonical flow.**
| Role | Survivor | Retire |
|---|---|---|
| Poller | `run_commander_directive_sweep.py`, stripped to fetch-only | its own inline classify/reply logic |
| Classifier | `core/comms/email_mode_classifier.py` | — |
| Router/verify | `core/comms/directive_executor.py` | — |
| Task store | `mission_board.json` via `mission_board_sync.add_mission()` | `email_task_ingest.py`'s separate JSON queue + `opencode_inbox.md` side-channel (its watcher is already orphaned per brief) |
| Reply sender | `dispatch_and_email.py` (threaded) | `email_c2.py` `[WING]` engine — already disabled; make retirement formal |

One inbox scan → one classify call → one mission-board write → one reply.

**Q2 — Task + response for every mode, including ACK/CC.** Fix Finding 1:
every inbound Commander email creates *some* mission-board row — weight
scales with mode, nothing is silently dropped.

| Mode | Mission | Status at creation | Reply |
|---|---|---|---|
| TASKING | Full mission, `assigned_to`=routed seat, `acceptance_criteria` set, `deadline_hours` set | OPEN | "Tasked to X, RDD Y, action: Z" |
| CC | Lightweight mission, `assigned_to`=seat inferred from CC'd content | OPEN until seat acts | "X is acting on this because Y; will confirm" |
| FYI | Lightweight mission, no seat, no acceptance criteria | auto-CLOSED at creation | "Filed, no action required" |
| ACK (Commander closing a Hale-opened loop) | **Not a new mission** — closes the referenced ticket via thread/ticket-id, not the classifier | CLOSED | "Acknowledged, ticket X closed" |

**Q3 — WHO/RDD/ACTION/DELIVERABLE.** Don't invent a new field set — wire
`_create_email_mission()` to actually populate `mission_board_sync`'s
existing schema (fixes Finding 2), then make every reply template
(`TASKED`/`DONE`/`LOGGED` in `directive_executor.py`) render the same
4-line block instead of free text:
```
WHO:         <assigned_to>
RDD:         <computed from deadline_hours>
ACTION:      <acceptance_criteria / one line>
DELIVERABLE: <verification_artifact or "pending">
```
This is a template change to existing `reply_text` construction, not new
infrastructure.

**Q4 — AG/CC routing.** Route through the builders that already exist —
`task_templates.build_ag_task/build_cc_task/build_oc_task`, gated by
`is_checkable()` — inside the TASKING branch of `route_email()`:
- **AG** (`contact_ag`) — vision/large-context work, or the cross-engine
  verification step itself.
- **CC** (`/ask-claude` from OC, or native when CC is the seat already
  running the inbox) — architecture/code judgment calls.
- **OC** — default/cheapest lane for mechanical or ambiguous-but-simple
  TASKING, per existing Task Precision Ladder doctrine (CLAUDE.md).
Overload guard: reuse `check_headroom()`/`route_task()` before assignment —
don't build a second capacity gate.

**Q5 — Verification without theater.**
- TASKING → `execute_directive()`'s existing cross-engine `verify_and_record()`
  gate. No change — it already refuses to self-certify.
- FYI/ACK → close at creation. No claim was made, so there is nothing to
  verify; running a cross-engine check on a no-op FYI is theater in the
  *other* direction (manufactured rigor over nothing).
- CC → closes when the routed seat's action is independently verified
  (same gate as TASKING) — CC is still Commander intent per non-negotiable
  #3, so it earns the same bar, not a lighter one.
- Rule of thumb: **verification effort scales with the size of the claim
  made, never with the mode label.**

## OPINION
- Fold ACK into thread/ticket-id linkage, not a 4th classifier mode. ACK is
  about direction (Commander closing *my* loop) not content — a classifier
  that only sees isolated message text structurally cannot detect that; it
  needs `In-Reply-To`/ticket-id threading on the reply path instead.
- Finding 2 (`assigned_to="unassigned"` hardcoded) is the highest-leverage
  single fix in this whole redesign — it silently defeats Q3's entire
  premise today, independent of anything else in the brief.
- The store and verification layer are not the problem — `mission_board_sync`
  and `directive_executor` are already doctrine-compliant. The problem is
  three unwired/duplicate front doors feeding them inconsistently.

## RECOMMENDATION
1. Retire `email_task_ingest.py` (queue + `opencode_inbox.md`) and formally
   decommission `email_c2.py` `[WING]`.
2. Strip `run_commander_directive_sweep.py` to fetch-only; route every
   message through `email_mode_classifier` → `directive_executor` — kill the
   second, disagreeing classifier.
3. Fix `_create_email_mission()` to populate `assigned_to`/`acceptance_criteria`/
   `deadline_hours` instead of hardcoding `"unassigned"`.
4. Extend `route_email()` to create a lightweight logged mission for FYI/CC
   (currently creates none) — closes the non-negotiable #2 gap.
5. Standardize `reply_text` across all three statuses to the WHO/RDD/ACTION/
   DELIVERABLE block.
6. Wire `task_templates.py` builders + `is_checkable()` into the TASKING
   branch for AG/CC/OC routing.
7. Add `In-Reply-To`/ticket-id threading so a Commander ACK closes a
   Hale-opened loop structurally, not via reclassification.
