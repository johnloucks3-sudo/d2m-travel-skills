## Pilot #3 — Priority-based auto-escalation (Item #1)

**BLUF:** P0/P1 missions idle >2h (no `updated_at` change) get auto-reassigned to a different seat via the existing `route_task()` router, capped at one auto-reroute per mission, always reported.

**Grounded in real code** (checked before drafting, not assumed):
- `OpsCenter/mission_board_sync.py` — missions already carry `status`, `priority`,
  `assigned_to`, `updated_at`, `logs`. No new schema needed.
- `core/relay/task_delegation.route_task()` — existing seat router, keyword-flag
  based (`needs_judgment`, `needs_large_context`, `is_vision`, `claude_optional`).
  Does not take "currently assigned seat" as an exclusion input — if it
  recommends the SAME seat already stuck, that's not a real escalation.

**Design:**
1. New script `scripts/mission_auto_escalate.py`, timer-driven (proposed: every
   30 min, matching the existing decision-matrix refresh cadence already
   established this session).
2. Scan active missions: `status in (active, in_progress, assigned, pending)`,
   `priority in (P0, P1)`, `now - updated_at > 2h`.
3. For each: call `route_task()` with a conservative default (no special flags
   — safe-default routing) to get a recommended seat.
4. **If recommended seat == currently assigned seat:** no real escalation
   available — fall back to notify-only for this mission (can't auto-reroute
   to nowhere), flagged distinctly from a real reroute in the report.
5. **If different:** reassign `assigned_to`, append a `logs` entry
   ("auto-escalated: idle >2h, {old_seat} → {new_seat}, reason: {rationale}"),
   set a `auto_escalated: true` / `escalation_count` field.
6. **Cap: one auto-reroute per mission**, ever (checked via `escalation_count`).
   A mission that stalls again after its one auto-reroute gets flagged to the
   Commander directly, not re-routed a second time — matches the existing
   anti-churning convention used elsewhere in this codebase (3-strikes-style,
   scaled down since a bad reroute has a higher cost than a bad OC retry).
7. **Always report** — every run that finds ANY escalation or notify-only
   case sends a Telegram summary (short) + logs to the mission's own history.
   A full email brief only if the run is non-empty (avoid inbox noise on
   empty runs — matches existing dossier-freshness / port-intel-trigger
   pattern from earlier tonight).

**Acceptance criteria (checkable):** a real active P0/P1 mission with
`updated_at` artificially backdated >2h gets its `assigned_to` changed to a
different seat, `escalation_count` becomes 1, a `logs` entry exists, and a
second run does NOT re-escalate it again (cap enforced).

**Risk / why this needed a real interview:** auto re-route is the higher-risk
option you chose over notify-only — a bad reroute could hand a
judgment-heavy mission to a seat unsuited for it. The one-reroute cap and the
"same seat = no real escalation, don't force one" rule are the two guardrails
against that; open to tightening further before this ships.

## Pilot #2 — Verification caching with TTL (Item #8)

**BLUF:** narrow scope — cache only checks that are provably re-run on the
same input within a session, not a blanket wrap of `integrity_check.py`.

**Grounded in real code:**
- `core/staffing/integrity_check.py` — `verify_and_record()` dispatches to
  AG/OC for cross-engine ground-truth checks. These are NOT good caching
  candidates (each one is meant to be a fresh, independent check — caching
  defeats the purpose of asking a different engine to look again).
- `core/silver/gate.py` — `run_gate()` is the better fit: deterministic,
  local checks (file-exists, non-empty, placeholder-scan, criteria-numbers)
  against a `(work_product, acceptance_criteria)` pair. These ARE provably
  re-run on identical input when the same artifact gets checked more than
  once in a session (e.g. this session re-verified the same 3 staged
  `.service` files across two dispatch rounds).

**Revised scope, matching "narrow" exactly:** cache `run_gate()`'s result
keyed on `(work_product_path + its mtime, acceptance_criteria)` — mtime in
the key means a real file change automatically invalidates the cache without
needing a manual TTL expiry for the common case; a TTL (proposed: 10 min)
covers the rest (non-path work products, or same-mtime-different-meaning
edge cases). Never cache `integrity_check.verify_and_record()` — that stays
always-fresh, cross-engine, no caching, full stop.

**Acceptance criteria (checkable):** calling `run_gate()` twice on the same
unchanged file+criteria returns the identical verdict object without a
second disk scan (verify via a call-counter on the underlying check
functions); touching the file and calling again produces a fresh check, not
a stale hit.
