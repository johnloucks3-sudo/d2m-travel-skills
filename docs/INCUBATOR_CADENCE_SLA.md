# Thunderbird AI Incubator — Cadence SLA
*Verified 2026-07-06. Supersedes the single-script/6-phase model in `docs/INCUBATOR_CADENCE.md` (superseded 2026-06-10 by supertimer consolidation — that doc's `agents/thunderbird_incubator.py` and `thunderbird-incubator.timer` never existed under those names; actual paths below).*

## Actual architecture (3 phases, 3 separate schedulers)

| Phase | Script invocation | Scheduler | Cadence | Status as of 2026-07-06 |
|---|---|---|---|---|
| **execute** (research scrape) | `core/intel/thunderbird_incubator.py execute` | `supertimer` → `ai_exec_bot.py` task `incubator-execute` (also a standalone `d2m-incubator-execute.timer`, now vestigial — always skips, real trigger is the supertimer) | every 43,200s (2x/day) | LIVE — fresh `incubator_raw_YYYY-MM-DD.json` daily |
| **evening_review** (A2 classify → ELON tickets → A5/A9 check → COS brief → build queue → Drive upload → Telegram) | `core/intel/thunderbird_incubator.py evening_review` | standalone `d2m-incubator-evening-review.timer` | daily 20:00 MDT | **WAS DEAD 2026-06-09 → 2026-07-06 (27 days)** — timer was `disabled`/`inactive`, dropped during the mid-June supertimer migration and never re-added anywhere. **RE-ENABLED 2026-07-06**, live-fire tested end to end (real signals → real ELON tickets → build queue write → Drive upload → Telegram) |
| **overnight_report** (build status digest → Gmail + Telegram) | `core/intel/thunderbird_incubator.py overnight_report` | standalone `d2m-incubator-overnight-report.timer` | daily 06:30 MDT | LIVE, but was reporting "no builds" every day for 27 days — symptom, not a separate fault, of evening_review being dead |

Output directory is `core/intel/intel/` (path is relative to the script's own location, not repo root — cosmetic nesting quirk, not a bug; all phases agree on it, so nothing is lost).

## Root causes found and fixed this session

1. **Evening-review timer orphaned during supertimer migration (~2026-06-09/10).** `execute` was added to the supertimer bot roster; `evening_review` was left behind as a disabled standalone timer and never wired into anything else. Nothing alerted on this because `overnight_report` still ran and sent a superficially normal "no builds last night" message every morning — a silent-sensor failure (system reported presence, not efficacy). **Fixed:** timer re-enabled (`systemctl --user enable --now d2m-incubator-evening-review.timer`), verified with a live manual run against today's real data — produced real A2 classifications, ELON tickets, a 5-item build-queue write, and a Drive upload.
2. **Query/content bug: bare "Thunderbird" search terms collide with Mozilla Thunderbird (the email client).** All 7 daily query sets led with a bare "Thunderbird ..." phrase; DuckDuckGo/Bing weighted "Thunderbird" so heavily that today's lead query returned 6/6 Mozilla-email-client results (Wikipedia, thunderbird.net, install guides) with zero relevance to the D2M AI stack. The LLM then dutifully classified this noise into fake ELON tickets ("integrate Thunderbird's value proposition as a free email application," "enhanced support for Windows users") — the evening review that just ran surfaced exactly this garbage before it was caught. **Fixed:** reworded the ambiguous "Thunderbird" lead term to "AI travel agency" across all 7 day-of-week query sets in `QUERIES_BY_DAY`.
3. **Telegram send timeout too tight (10s).** The live-fire verification run's own Telegram brief failed with a read timeout, silently dropping the notification (build queue and Drive upload still succeeded). Credentials were confirmed good with an out-of-band test send. **Fixed:** raised `_send_telegram` timeout 10s → 20s.

## Known unresolved issue (flagged, not fixed this session)
**DDG/Bing search backend appears to rate-limit after ~1 request per short session window** — repeated `_web_search()` calls made seconds apart during this verification returned 0 results regardless of query content, even for a query that had returned 6 results moments earlier. This is the likely explanation for the historical run of empty (`[]`, 2-byte) `incubator_raw_*.json` files seen on 2026-06-20 through 2026-06-24 and other scattered dates — not a one-off. `phase_execute()`'s query loop has no delay between the 3 sequential `_web_search()` calls. **Recommendation:** add a short delay (2-5s) between queries in the loop, or evaluate a paid/more reliable search backend if this proves chronic. Routed to Whetstone (A14, currency/CI) as a CI-freshness item — not fixed here because I could not get a clean rate-limit-free test window to validate a fix live.

## Failure notification / timeout policy (as designed in code, confirmed still accurate)
- Each phase writes a same-day sentinel file to `state/incubator_<phase>_<date>.done`; a phase that finds its own sentinel present skips (idempotent against timer restarts).
- `evening_review` aborts and pages Telegram (`🚫 INCUBATOR EVENING REVIEW ABORTED`) if the `execute` sentinel for today is missing — i.e., it already has a built-in dependency check and will not run on stale/missing data.
- No cross-phase retry-on-failure exists (e.g., if `execute` fails at its scheduled time, nothing automatically retries it before `evening_review`'s 20:00 trigger checks for the sentinel). This is a gap worth closing if `execute` failures become common; not currently observed.
- No automated **weekly uptime audit** exists yet. Recommend: Monday review comparing 7 days of `state/incubator_*.done` timestamps against the 3 expected times, surfaced in the Sunday ELON-proposal review cadence already on the books.

## Build queue integration — verified
- `intel/elon_build_queue.md` (physically at `core/intel/intel/elon_build_queue.md`) is written by `evening_review`, consumed for display only (not re-parsed) — the JSON twin `elon_build_queue.json` (loaded via `_load_build_queue()`/`_save_build_queue()`) is the actual read/write source of truth `overnight_report` checks against.
- Completed vs. pending items are NOT separated into distinct sections in the current markdown writer — every ticket from every day is appended to the same running list body, overwritten in full each evening_review run from the JSON queue's full history. This matches "not deleted," but there is no explicit "COMPLETED" heading split as the original spec asked for. Flagged for a follow-up if the Commander wants that structure; not changed this session to avoid touching queue-format logic beyond the three fixes above.
- ELON reads the queue only through `evening_review`'s own in-process build (it does not separately "read the queue daily" as a distinct 07:45 step — that step, and the 07:00/07:30 AM-scrape/A2-intake split described in the original March doc, were consolidated into the single 20:00 `evening_review` invocation at some point before this session; the git history and file timestamps confirm this consolidation, not a new change made here).
