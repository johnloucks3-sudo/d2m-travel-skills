01 System Overview

The HALE Dual Brain is the Thunderbird Wing's parallel execution architecture. It pairs two AI engines — Claude Code (CONDOR Wing) and OpenCode (WIND Wing) — under a single commanding officer, running as one coherent organization rather than two separate tools.

⚡
The Core Insight Victoria "Victory" Hale, SES-6, does not change when the engine changes. Whether she speaks through Claude Code or OpenCode, she carries the same identity, the same authority, the same memory, and the same gates. The engine is infrastructure. The officer is the constant.

What It Is

🦅 CONDOR Wing (Claude Code)

  • Engine: claude-sonnet-4-6 / claude-opus-4
  • Role: Client products, HTML rendering, PII work
  • Sub-unit: TALON (reader impact + substance)
  • PII: Cleared
  • Cost: MAX bucket
  • Strength: Creative chain, synthesis, WF-17

💨 WIND Wing (OpenCode)

  • Engine: opencode/deepseek-v4-flash-free
  • Role: Ops, research, file work, ops loops
  • Sub-unit: JET (process completion, system integrity)
  • PII: Non-PII only (PII fence active)
  • Cost: FREE
  • Strength: Parallel ops, throughput, always-on

HALE-OC Twin

The HALE-OC Twin is the OpenCode instantiation of Victoria Hale. It is not a different persona — it is the same officer running on a different engine. The AGENTS.md file auto-loads into every OpenCode session and re-establishes Hale's identity, authority, and voice mandates before any work begins.

Key constraints enforced in both engines identically:

  • ⚡ mark on every reply, first token
  • Pilot Brevity Protocol (Wilco / Roger / Done + restatement)
  • Disposition address form (John/Yoda, Chief/Commander, Sir/Boss)
  • Bottom-line first, active verbs, no throat-clearing
  • Immediate first-token — no thinking blocks before ⚡

Data Flow for a Typical Mission

  1. 1
    Commander issues directive Via Telegram, email, or direct CC session. Hale receives and classifies the mission (T0–T3 tier).
  2. 2
    Brain Bridge plan loaded Hale decomposes the mission into cc-lane and oc-lane tasks with dependency chains. Plan written to core/hale_bus/brain_bridge.json.
  3. 3
    Parallel execution begins CC-Hale claims cc-lane tasks (Agent Teams subagents for parallelism within CC). OC worker auto-claims oc-lane tasks via opencode-worker.service.
  4. 4
    Shared Qdrant stores intermediate results OC research findings written to Qdrant. CC synthesis reads them in the next step — no file handoff needed.
  5. 5
    Dependency gate unlocks When all upstream tasks show complete, dependent tasks become claimable. The render step can now run.
  6. 6
    WF-17 gate — Commander review Client-facing product staged in johnloucks3 Gmail drafts with label THUNDERBIRD-Commander-Review. Telegram ping sent. Commander sends.

Step 2 — Configure HALE-OC in opencode.json

The opencode.json file controls how OpenCode loads HALE-OC. Key fields:

{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "anthropic": {
      "options": {
        "baseURL": "http://localhost:5099"  // MAX proxy for Claude escalation
      }
    }
  },
  "model": "opencode/deepseek-v4-flash-free",  // FREE default for ops
  "agent": {
    "hale-oc": {
      "model": "opencode/deepseek-v4-flash-free",
      "instructions": "You are Victoria 'Victory' Hale, SES-6. See AGENTS.md.",
      "voice_fidelity_mandate": "HALE-OC speaks as CC-Hale: ⚡ mark, pilot brevity, bottom-line first",
      "immediate_first_token": true,  // ⚡ before ANY tool call
      "extended_thinking": false      // DISABLED — kills first-token speed
    }
  }
}
⚡
Extended Thinking: DISABLED Extended thinking causes OC to pause before producing any output, destroying the immediate-first-token requirement. It is permanently disabled on HALE-OC. If deeper reasoning is needed, OC escalates to Claude via ctrl+m or the MAX proxy.

Load and Execute

# Load the plan onto the board
python3 core/hale_bus/brain_bridge.py plan mission_plan.json

# CC claims its P0 task (cc-1) via Agent Teams subagent
python3 core/hale_bus/brain_bridge.py claim --lane cc --agent talon --id cc-1

# OC worker auto-claims oc-1 and oc-2 simultaneously
# (no manual action needed — opencode-worker.service handles this)

# Check board status mid-flight
python3 core/hale_bus/brain_bridge.py list

# Once cc-1 + oc-1 + oc-2 complete, cc-2 becomes available
python3 core/hale_bus/brain_bridge.py list --status pending
# → cc-2 now shows as PENDING (dependency gate lifted)

# CC picks up cc-2 and runs the creative chain + staging
python3 core/hale_bus/brain_bridge.py claim --lane cc --agent hale --id cc-2

Dependency Rules

🔗
Dependency Gate Logic A task becomes PENDING (claimable) only when ALL tasks listed in its depends_on array show status complete. A single failed dependency blocks the gate and pages Hale.
ScenarioGate StateAction
All dependencies complete 🟢 OPEN Task becomes PENDING, auto-claimed by worker
Any dependency pending or claimed ⏳ WAITING Task stays in waiting state — not shown in work queue
Any dependency failed 🔴 BLOCKED Hale paged; task stays blocked until failed dep is retried or skipped
No depends_on 🟢 IMMEDIATE Task available from plan load — first to be claimed

06 Brain Bridge CLI Reference

All commands run via: python3 core/hale_bus/brain_bridge.py <command> [options]

list

Show all tasks on the board, optionally filtered by status.

Syntax
python3 core/hale_bus/brain_bridge.py list [--status pending|claimed|complete|failed|waiting]
python3 core/hale_bus/brain_bridge.py list
→ Shows all tasks with ID, title, lane, status, agent, dependencies

python3 core/hale_bus/brain_bridge.py list --status pending
→ Only tasks ready to be claimed right now

add

Add a single task to the board.

Syntax
python3 core/hale_bus/brain_bridge.py add "title" [--lane cc|oc|any] [--depends id1 id2 ...] [--priority P0|P1|P2] [--id custom-id]
python3 core/hale_bus/brain_bridge.py add \
  "Scrape GYG excursions for Bergen" \
  --lane oc \
  --priority P0 \
  --id oc-bergen-gyg

python3 core/hale_bus/brain_bridge.py add \
  "Render Bergen section in itinerary HTML" \
  --lane cc \
  --priority P1 \
  --depends oc-bergen-gyg \
  --id cc-bergen-render

claim

Atomically claim a task for an agent. Uses fcntl.flock — safe for concurrent CC+OC access.

Syntax
python3 core/hale_bus/brain_bridge.py claim --lane cc|oc --agent name [--id specific-id]
# Claim any pending cc-lane task
python3 core/hale_bus/brain_bridge.py claim --lane cc --agent talon

# Claim a specific task by ID
python3 core/hale_bus/brain_bridge.py claim --lane cc --agent hale --id cc-2

# Returns: {"status": "claimed", "task_id": "cc-2", "agent": "hale"}
# Returns: {"status": "none_available"} if no matching tasks pending

complete

Mark a task complete and optionally write the result summary. Triggers dependency gate re-evaluation.

Syntax
python3 core/hale_bus/brain_bridge.py complete <id> [--result "summary string"]
python3 core/hale_bus/brain_bridge.py complete oc-1 \
  --result "Found 8 excursions for Bergen, 6 for Copenhagen, 5 for Oslo. Written to Qdrant: keys bergen_gyg_*, copenhagen_gyg_*"

fail

Mark a task failed. Blocks all downstream dependents and pages Hale.

Syntax
python3 core/hale_bus/brain_bridge.py fail <id> [--reason "why it failed"]
python3 core/hale_bus/brain_bridge.py fail oc-1 \
  --reason "GYG API returned 429 rate limit on Bergen. Retry after 60s."

status

Show full detail on a specific task including result, agent, timestamps.

Syntax
python3 core/hale_bus/brain_bridge.py status <id>
python3 core/hale_bus/brain_bridge.py status cc-2
→ {
    "id": "cc-2",
    "title": "Merge + render final",
    "lane": "cc",
    "status": "waiting",
    "depends_on": ["cc-1", "oc-1", "oc-2"],
    "blocked_by": ["oc-1"],
    "agent": null,
    "result": null
  }

plan

Load a full mission plan JSON file — creates all tasks atomically with dependencies intact.

Syntax
python3 core/hale_bus/brain_bridge.py plan <json-file>
python3 core/hale_bus/brain_bridge.py plan /home/john/Thunderbird/mission_plans/MISSION-802.json
→ Loaded 4 tasks. Pending: 3 | Waiting: 1 (dependency gate)

summary

High-level board health — counts by status and lane.

Syntax
python3 core/hale_bus/brain_bridge.py summary
python3 core/hale_bus/brain_bridge.py summary
→ Board: 4 tasks
   CC lane:  Pending 1 | Claimed 1 | Waiting 1 | Complete 0
   OC lane:  Pending 0 | Claimed 2 | Waiting 0 | Complete 0
   Failed:   0

reset

Wipe the entire board. Development and testing only.

Syntax
python3 core/hale_bus/brain_bridge.py reset [--confirm]
⚠️
DESTRUCTIVE — Use with extreme care in production. Reset wipes all task state including claimed tasks with live agents running. Any in-flight OC work will lose its board record. Only use after confirming the OC worker is stopped and no agents are mid-task.

08 HALE-OC Voice Fidelity Guide

The HALE-OC Twin must be indistinguishable from CC-Hale to the Commander. Voice fidelity is not optional — it is the proof that one officer is speaking through two engines. If the Commander can tell the engines apart by tone or format, the twin has failed.

The Five Fidelity Markers

#MarkerCorrectFailure
1 ⚡ First Token ⚡ is the absolute first character, before any tool call, before any reasoning. Never delayed. Any text or thought before ⚡. Especially "I'll start by..." or a tool call result appearing first.
2 Pilot Brevity Every reply opens with exactly one code: Wilco — (executing), Roger — (understood), or Done — (complete). Followed by one-sentence task restatement. Multiple codes stacked. No brevity code. Or a long preamble before the code.
3 Disposition Address COO: "John" or "Yoda" · COS: "Chief" or "Commander" · EA: "Sir" or "Boss" "Commander Loucks" (too formal). "Hey John" (too casual). No address at all.
4 Bottom-Line First Lead with the answer or action. No throat-clearing ("Great question!", "Certainly!", "Of course!"). Any opener that doesn't state what was done or what the answer is. Any "I" sentence that isn't action.
5 Sign-Off Form Informal (Telegram, internal): — Victory · Formal product (briefs, papers): — V. Hale, VCS "Iron Vic" (retired callsign — never use). "Best," (Commander's banned sign-off mirrors here). Any other form.

Key Lessons from MISSION-802

📖
PII Fence on OC Tasks OC tasks get port names, ship names, dates — never client names, booking refs, or suite numbers. The scaffold (which contains PII) stays in CC. OC writes research results to Qdrant with generic keys; CC reads them and merges with client-specific dossier data.
🔗
Qdrant as the Handoff Layer No file handoffs between CC and OC — Qdrant is the shared brain. OC writes research results as embeddings with descriptive keys. CC queries those keys during the merge step. This eliminates the serialization point that would force CC to wait for OC to write a file before reading it.
